# DUNGEON DESCENT

## MASTER PROMPT — UNITY 3D DARK FANTASY DUNGEON CRAWLER V1

Ты создаёшь С НУЛЯ новый качественный Unity-проект.

Это не тестовая сцена.
Это не техническое демо.
Это не набор кубов и капсул.
Это не временный прототип, который визуально выглядит как учебный проект.

Необходимо заложить фундамент полноценной 3D indie-игры уровня качественного vertical slice.

---

# 0. ГЛАВНАЯ КОНЦЕПЦИЯ

Рабочее название:

**DUNGEON DESCENT**

Жанр:

**3D Third-Person Dark Fantasy Action Dungeon Crawler**

Основная структура игры:

**SAFE ROOM → DESCENT → DUNGEON → COMBAT → LOOT → DEEPER FLOOR → BOSS / EXTRACTION → SAFE ROOM → UPGRADES → NEW RUN**

Игрок начинает не прямо в подземелье.

У него существует собственное безопасное помещение — его постоянная база.

Это место должно ощущаться как настоящий дом/убежище.

Из этой комнаты игрок лично:

1. подходит к двери;
2. взаимодействует с ней;
3. открывает её;
4. попадает к лестнице, ведущей глубоко вниз;
5. начинает физически спускаться;
6. атмосфера постепенно меняется;
7. безопасная музыка пропадает;
8. появляются звуки подземелья;
9. свет становится холоднее и темнее;
10. игрок оказывается внутри огромного данжа.

Никакого банального:

`Нажмите кнопку → Loading → Dungeon`

если технически возможно сделать более качественный переход.

Игрок должен ЧУВСТВОВАТЬ, что он покидает безопасный мир и самостоятельно спускается туда, откуда может не вернуться.

# 1. ОБЩАЯ ФАНТАЗИЯ ИГРОКА

Игровая фантазия:

> «У меня есть маленькое безопасное убежище над огромным неизвестным подземельем. Каждый раз я готовлюсь, открываю тяжёлую дверь и спускаюсь всё глубже туда, где находятся новые монстры, сокровища и опасности.»

Safe Room должна давать ощущение:

- безопасности;
- тепла;
- подготовки;
- постоянного прогресса;
- дома.

Dungeon должен давать противоположное ощущение:

- неизвестности;
- опасности;
- масштаба;
- темноты;
- древности;
- тревоги;
- желания посмотреть, что находится ещё глубже.

Контраст этих двух состояний является одной из центральных частей игры.

**URP**

**3D**

# 6. ДВЕРЬ В ПОДЗЕМЕЛЬЕ

Это важнейшая часть атмосферы.

Не делать обычный моментальный teleport.

Когда игрок взаимодействует с дверью:

1. управление на короткое время корректно переключается;
2. персонаж подходит к двери;
3. кладёт руку на ручку;
4. ручка поворачивается;
5. тяжёлая дверь начинает открываться;
6. слышится металл/камень/дерево;
7. из пространства за дверью приходит холодный свет;
8. появляется далёкий dungeon ambience;
9. камера слегка меняет композицию;
10. дверь полностью открывается;
11. контроль возвращается игроку.

За дверью находится настоящий проход.

# 7. СПУСК

За Safe Room начинается длинная лестница вниз.

Игрок должен самостоятельно пройти по ней.

Лестница постепенно меняется.

В начале:

- тёплое освещение;
- нормальные стены;
- звуки Safe Room ещё слышны.

Ниже:

- свет становится слабее;
- появляются древние стены;
- увеличивается влажность;
- возникают трещины;
- появляются цепи;
- паутина;
- капли воды;
- корни;
- древние символы.

Ещё глубже:

- начинает слышаться ветер;
- далёкие крики;
- рычание;
- металлические удары;
- неизвестные звуки.

Safe Room остаётся далеко сверху.

Игрок входит в первый настоящий Dungeon Hub.

Не делать полностью хаотическую procedural generation, превращающую уровни в бессмысленный набор одинаковых комнат.

Использовать:

**authored modular dungeon generation**

Создать качественные вручную подготовленные модули:

- SmallRoom;
- MediumRoom;
- LargeRoom;
- Corridor;
- TIntersection;
- CrossIntersection;
- StairDown;
- TreasureRoom;
- CombatArena;
- EliteArena;
- SecretRoom;
- BossEntrance;
- BossArena.

DungeonGenerator собирает допустимые комбинации.

Использовать seed.

Каждый run может немного отличаться, но архитектура должна оставаться логичной.

# 13. ROOM SYSTEM

Каждая dungeon room должна иметь собственное состояние.

Пример:

`Unvisited`

→

`Entered`

→

`CombatLocked`

→

`Cleared`

→

`RewardAvailable`

После входа в combat room:

- двери могут закрываться;
- появляется encounter;
- начинается combat music;
- после убийства врагов двери открываются.

Но не превращать ВСЕ комнаты в одинаковые закрытые арены.

Часть встреч должна происходить естественно во время исследования.

# 14. PLAYER CONTROLLER

Управление должно ощущаться современно.

Игрок умеет:

- ходить;
- бегать;
- sprint;
- быстро разворачиваться;
- dodge roll / evade;
- атаковать;
- делать heavy attack;
- block;
- взаимодействовать;
- использовать potion;
- lock-on на врага.

Перемещение не должно:

- скользить;
- выглядеть как движение манекена;
- моментально менять направление без анимации;
- ломать ноги персонажа;
- иметь foot sliding.

---

# 15. КАМЕРА

Third-person камера.

Не прибивать камеру жёстко к персонажу.

Она должна:

- плавно следовать;
- иметь collision avoidance;
- не проходить через стены;
- слегка адаптироваться к скорости движения;
- поддерживать combat;
- поддерживать lock-on.

Во время исследования камера свободнее.

Во время lock-on:

- игрок и противник остаются читаемыми;
- камера не должна хаотично вращаться;
- при нескольких противниках target можно переключать.

Добавить лёгкий camera impulse при тяжёлых ударах.

Не злоупотреблять shake.

---

# 16. COMBAT SYSTEM

Бой должен быть простым для понимания, но отзывчивым.

Базовые действия:

### Light Attack

Быстрый удар.

Можно объединить в combo.

Например:

Attack 1

→ Attack 2

→ Attack 3

---

### Heavy Attack

Более медленная атака:

- больше damage;
- больше stagger;
- больше commitment.

---

### Dodge

Использует stamina.

С коротким окном invulnerability.

---

### Block

Снижает/отменяет damage.

---

### Perfect Block / Parry

Опциональная более продвинутая механика.

Правильный момент:

- stagger врага;
- звук;
- VFX;
- короткая камера reaction.

---

# 17. HIT FEEDBACK

- animation reaction;

- звук;

- краткий hit pause;
- camera impulse;
- particle burst;
- weapon trail;
- stagger.

# 75. ОБЯЗАТЕЛЬНЫЕ ИНСТРУКЦИИ ПО АССЕТАМ И ПЕРЕДАЧЕ ПРОЕКТА

### 1. НИКАКИХ ЗАГЛУШЕК

В финальном проекте запрещены временные визуальные заглушки:

- Unity Capsule вместо персонажа;
- Cube/Plane вместо окружения;
- примитивные враги;
- placeholder UI;
- тестовые одноцветные материалы;
- временные звуки;
- пустые сцены;
- технические модели без нормального визуала.

Все игровые элементы должны быть приведены к качественному состоянию.

Разрешается и рекомендуется:

- находить подходящие легальные ассеты в интернете;
- использовать качественные бесплатные/разрешённые модели;
- брать текстуры и изображения из разрешённых источников;
- генерировать собственные изображения и текстуры;
- создавать/обрабатывать материалы;
- комбинировать и дорабатывать ассеты;
- самостоятельно создавать необходимые визуальные элементы;
- находить и использовать разрешённую музыку;
- находить ambient sounds и SFX;
- редактировать звук под игру.

Для любых сторонних материалов проверять лицензию и сохранять источник в `THIRD_PARTY_ASSETS.md`.

Цель: при запуске пользователь должен видеть ИГРУ, а не набор временных Unity-заглушек.

### 2. МИНИМУМ ВОПРОСОВ ПОЛЬЗОВАТЕЛЮ

Не останавливать разработку постоянными вопросами:

- «Продолжать?»
- «Создать этот файл?»
- «Использовать этот вариант?»
- «Перейти к следующему этапу?»
- «Можно ли добавить это?»
- «Подтвердите выполнение».

Если решение не критично и существует разумный профессиональный вариант — принять решение самостоятельно и продолжить работу.

Пользователь даёт большой уровень самостоятельности.

Самостоятельно:

- выбирать структуру;
- исправлять мелкие проблемы;
- выбирать подходящие ассеты;
- принимать технические решения;
- создавать недостающие элементы;
- улучшать визуал;
- исправлять баги;
- проводить polish;
- тестировать результат.

Не превращать разработку в последовательность из десятков запросов подтверждения.

### 3. ПРОЕКТ ДОЛЖЕН ПЕРЕДАВАТЬСЯ ЦЕЛИКОМ

После завершения рабочего этапа пользователь должен получить полный актуальный Unity-проект.

Допустимы два основных способа.

#### Вариант A — ZIP

Создать полный ZIP-архив проекта, который можно:

1. скачать;
2. распаковать;
3. открыть через Unity Hub;
4. запустить без ручного восстановления десятков отсутствующих файлов.

Не включать ненужные временные Unity cache-файлы, если они могут быть автоматически восстановлены, но все исходники, Assets, Packages, ProjectSettings и необходимые project files должны присутствовать.

---

#### Вариант B — GITHUB

Предпочтительный вариант для длительной разработки.

Организовать workflow аналогично предыдущей работе с Unity-проектом Skinny to Beast / Gym Tapper.

Для НОВОЙ игры создать отдельный GitHub repository.

Не использовать старый игровой репозиторий для нового Dungeon-проекта.

Рабочая схема:

**AI / разработчик**

→ изменяет Unity-проект

→ выполняет проверки

→ делает Git commit

→ отправляет изменения в GitHub через `git push`

↓

**Пользователь**

на своём компьютере получает изменения простой командой:

```bash
git pull
```

или, если используется отдельная рабочая ветка:

```bash
git pull origin <branch-name>
```

После этого обновлённые файлы Unity-проекта должны появляться непосредственно в локальной папке проекта пользователя.

Пользователь не должен вручную:

- копировать десятки файлов;
- вставлять каждый C#-скрипт;
- скачивать отдельные ассеты;
- создавать папки по инструкции;
- вручную восстанавливать сцену.

Git должен быть основным каналом синхронизации проекта.

---

### 4. GIT WORKFLOW

После создания нового repository определить основную рабочую ветку.

Например:

```bash
main
```

и при необходимости:

```bash
development
```

или отдельную feature-ветку.

В процессе разработки:

```bash
git status
git add .
git commit -m "описание изменения"
git push
```

На компьютере пользователя обычное обновление проекта должно сводиться в идеале к:

```bash
git pull
```

После pull пользователь открывает проект в Unity и проверяет новую версию.

---

### 5. НЕ ЛОМАТЬ WORKFLOW

После того как GitHub workflow настроен:

- не создавать новый repository без причины;
- не менять рабочую ветку хаотично;
- не заставлять пользователя каждый раз заново клонировать проект;
- не передавать отдельные куски вместо полного состояния проекта;
- не терять `.meta` файлы Unity;
- не коммитить `Library`, `Temp`, `Logs` и другие автоматически генерируемые тяжёлые каталоги;
- обязательно использовать правильный `.gitignore` для Unity.

Все Unity `.meta` файлы для Assets должны храниться в Git.

Это критично для сохранения GUID и ссылок между:

- сценами;
- prefabs;
- materials;
- animations;
- scripts;
- textures;
- ScriptableObjects.

### 6. ФИНАЛЬНОЕ ПРАВИЛО

Задача считается переданной пользователю только тогда, когда существует один из двух результатов:

**A. Готовый ZIP полноценного Unity-проекта**

или

**B. Все актуальные изменения отправлены в GitHub, и пользователь может получить их обычным `git pull`.**

Не заканчивать работу передачей нескольких фрагментов кода и инструкцией:

> «Теперь создайте эти файлы вручную».

Цель — максимально автоматизированная разработка и передача готового состояния проекта.
